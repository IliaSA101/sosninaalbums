# api/albums — контракт /v1 сервиса листалок Sosnina Albums

Открытый контракт: программа выгружает страницы фотоальбома, сервис хранит их и отдаёт клиенту по ссылке.
Лицензия модуля — Apache-2.0 (файл LICENSE). Зависимостей нет (yaml нужен только тесту сверки с OpenAPI).

- `v1/openapi.yaml` — источник истины (OpenAPI 3.1), встроен в пакет как `albums.OpenAPI`.
- `albums.go`, `check.go`, `validate.go` — типы и проверки: `Validate`, `ValidateCreate`, `ValidatePatch`,
  `ParsePageN`, `CheckID`, `CheckToken`, `CheckPassword`. Одни и те же и в программе, и в сервисе: сервис
  вызывает их на входе и пишет `manifest.json` повторной сериализацией типа `Manifest`, не сырыми байтами.
- `client.go`, `transport.go`, `base.go`, `errors.go` — Go-клиент: https (http только к loopback), токен
  только в `Authorization`, без переходов 3xx, ответ не больше 1 МБ, ошибки без адреса, `id` и токена.
- `albumstest/` — поддельный сервер по контракту (`New`, `NewFake`) и `Conformance`.
- `cmd/albums-fake` — тот же сервер процессом для стенда: `albums-fake -addr 127.0.0.1:34190 -dir /abs/папка -token <строка>`.

## Проверить свою реализацию

```go
func TestMyServiceConformance(t *testing.T) {
	albumstest.Conformance(t, "https://test.example.org", token, albumstest.WithOtherToken(otherToken))
}
```

**Только на тестовом экземпляре сервиса:** набор создаёт, правит и удаляет альбомы этого токена.
Он проверяет и безопасность: 401 без токена и с чужим, одинаковый 404 для чужого, удалённого и
несуществующего `id`, `id` не короче 22 знаков и первый не «-», пароль не в ответах API и не в
`manifest.json`, хэш и сигнатура страницы (409/400/413), закрытые страницы альбома с паролем, сброс
входов, `Content-Type: image/*` и `X-Content-Type-Options: nosniff`.

## Соглашения вне /v1

Просмотр клиентом (`/a/<id>/…`) вне `/v1`, но Conformance ждёт эти правила (они же в `v1/openapi.yaml`):

- `GET /a/<id>/` — страница альбома, 200; `/a/<id>/manifest.json` — манифест; файлы страниц лежат под
  именами из поля `file` манифеста (имя выбирает сервис, набор берёт его из манифеста).
- Неопубликованный, истёкший, удалённый и несуществующий альбом отвечает 404 на всех адресах `/a/<id>/…`
  (неопубликованное не раскрывается).
- Вход: `POST /a/<id>/login` (форма, поле `password`). Верный пароль — `Set-Cookie`. Неверный — любой ответ
  (401, 403 или 200 со страницей формы), после которого доступа нет: cookie на неверный пароль (если она
  выдана) не открывает ни одного адреса `/a/<id>/…` — ни страницу, ни `manifest.json`, ни файлы страниц.
- Страница `/a/<id>/` отдаётся с `Referrer-Policy: no-referrer` (id в адресе — ключ доступа). На https cookie
  входа — `Secure` и `HttpOnly`.
- Страница с неверными байтами: сигнатура и хэш проверяются на PUT; какой из двух отказов (400 `bad_page` или
  409 `hash_mismatch`) вернётся первым, контракт не фиксирует.

Картинки набора несут случайную соль на каждый прогон: сервис, который хранит страницы по хэшу, не
увидит в повторном прогоне «уже есть».
