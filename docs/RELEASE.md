# Выпуск сборки

Чек-лист для каждой сборки, которая уходит пользователю (exe) или на GitHub (`main`).

## 1. Версия

- `wails.json` → `info.productVersion`: семвер, `0.X.0` — новая функциональность, `0.X.Y` — исправления. Это единственный источник: Go встраивает его через `go:embed` в `main.go` и передаёт в `app.Run` (разбор — `internal/app/version.go`), версия видна в шапке окна и пишется в `log.txt` при запуске.
- Строка `Status` в `README.md` (английская, в начале файла) — та же версия.
- Строка в «Что нового» (ниже, раздел 5) — для пользователя, без технических слов.
- Сверка перед меткой: `node scripts/release-check.mjs --version X.Y.Z` — версия в `wails.json`, README «Status», `whatsnew.ts` и раздел CHANGELOG, спеки версии в таблице `docs/specs/README.md`, `needs` публикации в `release.yml`, эталоны для arm64. Код выхода ≠ 0 — не ставить метку. Тесты скрипта — `node --test "scripts/*.test.mjs"` (в CI).

## 2. Проверки (всё зелёное, ноль предупреждений)

```
powershell -ExecutionPolicy Bypass -File scripts/check.ps1 -Race
```

gofmt, go vet, golangci-lint, `go test -race` (нужен gcc, см. CLAUDE.md), prettier, eslint, svelte-check, vitest, сборка фронта, размер файлов, эталон тестов. Эталон силы тестов (`testdata/test-baseline.json`, `scripts/test-baseline.mjs`): счёт «имя теста → сколько раз» (Go — с подтестами, vitest — полное имя) и покрытие Go-пакетов (не ниже эталона минус 0,5 п. п.); провал, если по имени стало меньше (перенос в другой пакет/файл под тем же именем допустим). Обновляется только `node scripts/test-baseline.mjs --write`, с причиной в сообщении коммита и с согласия владельца, если что-то уменьшилось. Перед публикацией на GitHub дополнительно — `govulncheck ./...` и `npm audit --omit=dev` в `frontend`.

QA по `docs/QA.md`: затронутые циклом пункты, консоль браузера без ошибок и предупреждений. Для релиза с изменениями формата `.salbum` — открыть альбом прошлой версии.

Заставка, снимок и ролики README (`docs/media/`, mp4-вложения GitHub) — раздел «Ролики README» ниже: решить, перезаписывать ли, до подъёма версии; запись — после него.

## 3. Сборка

```
powershell -ExecutionPolicy Bypass -File scripts/build.ps1
```

Локальная сборка — проверка до публикации и выдача exe до выхода на GitHub; файлы для GitHub Release собирает Actions (§6). Скрипт делает `wails build -clean -trimpath` (с `GOTMPDIR`), переименовывает exe по версии из `wails.json` и проверяет, что в exe нет личных путей. Результат — `build/bin/SosninaAlbums-X.Y.Z.exe` (один файл, установка не нужна). WebView2: в Windows 11 он встроен; в Windows 10 при его отсутствии exe сам предложит скачать загрузчик (режим `-webview2 download` по умолчанию). Если у пользователя нет интернета — собирать с `-webview2 embed`.

## 4. Смоук собранного exe (2 минуты, руками)

1. Запустить: окно открывается, в шапке нужная версия, миниатюры грузятся (белое окно или пустые миниатюры — это CSP или WebView2).
2. Запустить второй раз — активируется уже открытое окно, второе не появляется.
3. Добавить папку, автосборка, листание раскладок, экспорт одного альбома в пустую папку, «Открыть папку».
4. Закрыть и открыть — альбом на месте.
5. `%APPDATA%\SosninaAlbums\log.txt` — строка «запуск, версия X», ошибок нет.

## 5. Передача пользователю

- exe. Опросник Марины и анкета для тестировщиков (`docs/private/make_docx.py`, `make_beta_docx.py`) — **только по отдельному запросу владельца** (владелец 2026-10-21: «не используется»); в план версии не ставить.
- Unsigned exe: SmartScreen («Подробнее» → «Выполнить в любом случае»), антивирус может спросить — инструкция в «Как установить».

## 6. Git

- Коммиты цикла — в локальной `dev`, без атрибуции Claude, автор — владелец репозитория.
- На GitHub — только `main` (один коммит на версию) и метки `vX.Y.Z`; каждый push — только после явного «да» владельца.
- В публичный `main` идут версии с новой функциональностью (`0.X.0`) и исправления `0.X.Y`, когда они нужны пользователям или чинят CI на `main` (0.9.1 — по решению владельца).
- Публикация версии на GitHub (с 0.9.1, сборка — `.github/workflows/release.yml`):
  1. До метки: `wails.json` → `X.Y.Z`, раздел `## X.Y.Z — дата` в `CHANGELOG.md` пользовательским языком (он целиком идёт в текст релиза), `frontend/src/shell/dialogs/whatsnew.ts` обновлён (версия и 4–6 строк «Что нового» для стартового окна), `THIRD_PARTY_NOTICES.txt` перегенерирован, §2–4 пройдены на локальной сборке. Ролики README — по разделу «Ролики README» ниже: перезапись решена — запись после подъёма версии, `--publish`, загрузка mp4 и их адреса в README; не решена — в README остаются прежние адреса. В обоих случаях `grep -n TODO-README-MEDIA README.md` пуст.
  2. `node scripts/publish-main.mjs <коммит dev> -m "Sosnina Albums X.Y.Z"` (без внутренних доков, список — `scripts/publish-exclude.txt`) → `git push origin main` → дождаться зелёного CI на этом коммите.
     Служебный коммит в main без выпуска (например, workflow): `node scripts/publish-main.mjs <коммит dev> --only <путь>… -m "ci: …" [--dry]` — поверх прежнего main берёт из dev только указанные пути; отказывает при расхождении с `origin/main` и при путях из `publish-exclude.txt`; `--dry` показывает `A/M/D` и статистику, ничего не меняя.
  3. `git tag vX.Y.Z main && git push origin vX.Y.Z` — Actions «Release» собирает exe Windows, `.app` macOS и бинарник Linux, задание «Архивы выпуска» (`pack`, `scripts/win/pack.py` и `pack_linux.py`, спеки 039 и 101) пакует их в два zip и один tar.gz с папкой `Sosnina Albums X.Y.Z`, рядом строит `.deb` (`scripts/linux/deb.sh`) и создаёт **черновик** релиза: `SosninaAlbums-X.Y.Z-windows-x64.zip`, `SosninaAlbums-X.Y.Z-macos-universal.zip`, `SosninaAlbums-X.Y.Z-linux-amd64.tar.gz`, `SosninaAlbums-X.Y.Z-linux-amd64.deb`, `THIRD_PARTY_NOTICES.txt`, инструкции (ниже) и текст (шаблон `.github/release-notes.md` + раздел CHANGELOG), ~15 мин. Голого exe на странице нет. Внутри каждого архива: программа, «Как установить (Windows|Mac|Linux).pdf» (нет pdf — docx), «Что нового.txt» (раздел CHANGELOG), `THIRD_PARTY_NOTICES.txt`, `LICENSE` и `NOTICE.md` (п. 4 и 6 GPL: копия лицензии вместе с программой; `pack.py check` отказывает архиву без любого из них; в tar.gz ещё значок `sosninaalbums.png`, в `.deb` лицензии лежат в `/usr/share/doc/sosninaalbums/`). Вызов: `pack.py <windows|macos|linux> … --notices THIRD_PARTY_NOTICES.txt --license LICENSE --notice NOTICE.md`.
  4. Публикация черновика — оркестратор, тем же «да» владельца на выпуск (владелец 2026-10-18: «сразу публиковать Release… с моего подтверждения тут»): после зелёных заданий Release (включая «Проверка Mac») сверить ассеты черновика (`gh release view vX.Y.Z --json assets,isDraft`) — два zip, tar.gz и .deb Linux, THIRD_PARTY, инструкции — и `gh release edit vX.Y.Z --draft=false`. Смоук zip Windows ниже — владелец по желанию после публикации (оркестратор exe не запускает). Прежний порядок для ручной проверки: Releases → черновик: скачать zip Windows, распаковать («Извлечь все») и запустить `SosninaAlbums.exe`, смоук §4 (zip Mac — если есть на чём проверить); задание «Проверка Mac» (smoke.sh на macOS-раннере) уже прошло на итоговом zip с папкой — иначе черновика нет; к черновику приложены шесть вариантов инструкции `SosninaAlbums-X.Y.Z-install-guide[-windows|-linux|-macos-26|-macos-15|-macos-12-14]-ru.docx` (и pdf, если справился LibreOffice) — собираются из [docs/install/guide.md](install/guide.md) (устройство — спека 029); седьмой вариант `…-install-guide-macos-ru` лежит только внутри архива Mac. Ошибка упаковки (`pack.py` или `check`) — провал задания `pack`, черновика нет. При желании поправить текст → «Publish release».
  5. Раздавать exe новой версии (Марине тоже) — только после push метки `v<версия>`: ссылки «О программе» ведут на метку, до неё они открывают пустую страницу.
  - Падение: сбой сети/раннера — «Re-run failed jobs»; ошибка в `release.yml` — исправить в dev, перенести в `main` только этот файл отдельным коммитом, push, затем Actions → Release → «Run workflow» с меткой `vX.Y.Z` (код берётся из метки). Метку не перевешивать: неверная версия в `wails.json` или несобираемый код — выпуск `X.Y.Z+1`. Запасной путь — локальная сборка и Mac по `docs/BUILD-macOS.md`, `gh release create … --draft` руками с теми же именами файлов.
  - До метки: раздел `## X.Y.Z` в CHANGELOG обязателен — из него `pack.py` режет «Что нового.txt» (нет раздела — в файле только заголовок и ссылка, предупреждение в логе).
  - Повторный прогон обновляет тот же черновик; опубликованный релиз workflow не трогает.
- Лицензии: код — GPL-3.0-only с дополнительным условием п. 7(b) об имени и логотипе (`LICENSE` — чистый текст GPL v3, ни строчки сверху и снизу: GitHub узнаёт лицензию только по нему; `NOTICE.md` — авторское право, условие 7(b), история: версии до 0.22.x выпущены под MIT). Единый файл `THIRD_PARTY_NOTICES.txt` (Go-модули отдельно под Windows, macOS и Linux через `go list` с тегами сборки, у модуля пометка ОС, если он не во всех трёх; npm-пакеты сборки, шрифты OFL, системные библиотеки Linux, полные тексты) генерируется `node scripts/third-party.mjs` из корня (нужны `go` и `frontend/node_modules`; go-licenses не нужен: он работает только под ОС машины); перед публикацией перегенерировать, diff пустой или объяснён. `LICENSE`, `NOTICE.md` и `THIRD_PARTY_NOTICES.txt` кладутся в каждый архив (`pack.py`) и в `.deb`; `THIRD_PARTY_NOTICES.txt` — ещё и отдельно в релиз (workflow берёт его из коммита метки). Шрифты в exe отдельно не продаются и не переименовываются; урезанные файлы — только у шрифтов без Reserved Font Name.

## Ролики README

В README: заставка `docs/media/demo.webp` (анимированный WebP 960×600, 12–16 с, ≤ 2,5 МБ) — вверху английской части; снимок `docs/media/screenshot.jpg` (1600×1000, ≤ 400 КБ) — в разделе «Как это выглядит»; ролики A «Автосборка и листание» и B «Раскладки: бросок и перебор» (mp4 1600×1000, 25–35 с, ≤ 9,5 МБ) — вложения GitHub, в git их нет, в README (в обеих частях) — их адреса. Фото — только Pexels из `scripts/demo/photos.txt`, авторы — `docs/media/CREDITS.md`. Устройство — спека 102 (`docs/specs/0.23/102-readme-video.md`).

**Когда перезаписывать** (реш. 102-10). Перед выпуском сравнить листы кадров прошлой записи (`sheet-A.jpg`, `sheet-B.jpg` её каталога прогона) с нынешним интерфейсом: шапка, лента, холст, окна «Автосборка» и «Варианты». Заметно изменилось — перезапись; нет — ролики, WebP и снимок не трогать: каждая новая WebP — ещё 2–2,5 МБ в истории `main` навсегда. Номер версии в шапке кадра сам по себе поводом не считается.

**Запись** (оркестратор, Ubuntu: GStreamer с `x264enc` и `mp4mux`, Python venv e2e с Playwright и Pillow — путь в `.claude/LOCAL.md`; ≈ 4 мин):

1. Только **после подъёма версии** в `wails.json` (§6, шаг 1) и коммита: версия видна в шапке каждого кадра, запись до подъёма покажет прошлую.
2. Замороженная копия этого коммита — правки в рабочем дереве не перезапустят стенд посреди записи:
   ```
   git worktree add --detach .gotmp/demo-tree <коммит с новой версией>
   ln -s "$PWD/frontend/node_modules" .gotmp/demo-tree/frontend/node_modules
   ```
3. Стенд `demo` из её корня (в фоне, порт 34119; 34115 — владельца, 34116 — QA): `cd .gotmp/demo-tree && env -u DISPLAY -u WAYLAND_DISPLAY scripts/stand.sh demo 34119`. У стенда свои папки данных `SosninaAlbums-stand-demo`; альбом в записи не сохраняется («Черновик»).
4. Из корня основного дерева (тогда `--publish` пишет в его `docs/media/`): `python3 scripts/demo/demo.py all --port 34119`. Прогон — `.gotmp/demo/<ГГГГММДД-ЧЧММСС>/`: `A.mp4`, `B.mp4`, `demo.webp`, `screenshot.jpg`, `sheet-A.jpg`, `sheet-B.jpg`, `summary.md`. Коды выхода: 0 — готово; 2 — нет стенда, фото, Pillow, GStreamer или неверный аргумент; 3 — личный путь в тексте страницы; 4 — сцена не дождалась результата (в сообщении — метка); 5 — бюджет размера; 6 — ошибки консоли или `log.txt` стенда.
5. Просмотр: `summary.md` (длительности, размеры, к/с захвата, консоль и приватность — чисто) и глазами `sheet-A.jpg`, `sheet-B.jpg`: в шапке новая версия, курсор виден и не прыгает, броски попадают в цель, нет окон-ошибок, тостов, пустых миниатюр, долгого «подбираем раскладки…». Плохо — поправить сцену в `scripts/demo/scenes.py` и повторить (до трёх кругов).
6. Годный прогон — `python3 scripts/demo/demo.py compose --run .gotmp/demo/<прогон> --publish` (или сразу `all … --publish` в п. 4): при коде 0 `demo.webp` и `screenshot.jpg` копируются в `docs/media/`. Коммит в dev вместе с подъёмом версии.
7. Стенд остановить (по PID своего `wails dev`), копию убрать: `git worktree remove --force .gotmp/demo-tree`.

**Адреса mp4** (Д5; только с «да» владельца на выпуск — это запись в публичный репозиторий, реш. 102-3). В публичном репозитории — один закрытый issue «README media» — №13 (создан 23.10 при выпуске 0.23.0). Загрузка: `gh issue comment <N> --repo IliaSA101/sosninaalbums --attach .gotmp/demo/<прогон>/A.mp4 --attach .gotmp/demo/<прогон>/B.mp4 --body "X.Y.Z"`, затем `gh api repos/IliaSA101/sosninaalbums/issues/comments/<id> --jq .body` — в теле два адреса `https://github.com/user-attachments/assets/<uuid>` в порядке вложений. Запасной путь — владелец бросает mp4 в поле комментария на сайте (не отправляя) и копирует адрес. Вложения закрытого `sosninaalbums-dev` не годятся: они требуют входа.

**Заглушка.** Пока mp4 не загружены, вместо адресов в README стоят строки `https://github.com/user-attachments/assets/TODO-README-MEDIA-A` и `…/TODO-README-MEDIA-B` — в английской шапке и в «Как это выглядит», каждая по два раза. Подстановка: все вхождения `TODO-README-MEDIA-A` и `TODO-README-MEDIA-B` заменить на `<uuid>` из адресов — до `publish-main.mjs`; после — `grep -n TODO-README-MEDIA README.md` пуст. Адрес — отдельной строкой без разметки: Markdown GitHub вырезает `<video>`, а голую ссылку на вложение страница репозитория показывает плеером. После выпуска открыть README на github.com: заставка движется, оба ролика играют (критерий 102-14).
