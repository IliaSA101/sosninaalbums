## Чтение папок и цвет (`internal/library`)

`Scanner` (`scan.go`) обходит папки, читает заголовки `NumCPU` воркерами и помнит прочитанное (путь → размер, mtime, `Photo`): «+ Папка», «Убрать папку» и Undo не перечитывают старые файлы. Список фото уходит в `library` порциями, всегда префиксом в естественном порядке — лента растёт, не прыгая. `App.rescan` не блокирует: прежнее сканирование отменяется, отчёты устаревшего поколения (`scanGen`) отбрасываются, убранная папка исчезает из ленты сразу; события отправляются под `emitMu`, а не под `a.mu`, чтобы `/media` не ждал IPC.

Отметки Lightroom (спека 004, только чтение): `Photo.Xmp *Marks` (`rating` 0–5, `label` red|yellow|green|blue|purple|other + `labelText` у other, `flag` 1/−1; `nil` — отметок нет, событие `library` не растёт). Заголовок JPEG читает `jpegSegments` (`imgfile/jpeghead.go`, бывший `jpegColorSegments` из `icc.go`): за тот же проход до SOS, что ориентация и ICC, сохраняет первый APP1 с основным пакетом XMP (`http://ns.adobe.com/xap/1.0/\0`; расширенный не читается) — лишнего ввода-вывода нет. Разбор — `parseXMP` (`xmp.go`): быстрый отказ без `Rating`/`Label`/`pick`, потоковый `encoding/xml` (`Strict`, без сущностей), пространства имён по URI, пакет ≤ 1 МБ (`maxXMPBytes`). Сайдкары: `walk` собирает `*.xmp` — только обычные файлы (ссылки и junction не читаются), размер и время из листинга, не больше `maxSidecars` = 100 000 за сканирование (дальше — строка в log.txt); у фото `имя.jpg` кандидаты `имя.jpg.xmp` (darktable, digiKam), затем `имя.xmp` (Lightroom, Bridge); открывается только найденное обходом. Сайдкар > 1 МБ по листингу не открывается, на чтении — `LimitReader` с повторной проверкой. Слияние по полям: сайдкар главнее встроенного по каждому полю, которое в нём встретилось (`mergeMarks`); `Rating = −1` — оценка 0 и флажок «отклонено», такой отказ встроенного снимается, если сайдкар задал рейтинг без флага (отказ из `pick` остаётся). Память сканера (`memoEntry`) хранит и размер/mtime сайдкара: запись верна, только если совпали и фото, и сайдкар (появился, пропал, изменился — фото перечитывается); сайдкар не открылся — результат не запоминается. Битый XMP фото нечитаемым не делает (`Xmp = nil`), строк об ошибках XMP за сканирование ≤ 20 (`xmpLog`), остальное — сводкой. `ReadInfo` (для `project.refresh`) отметки не читает: ему нужны размеры; отметки в `Editor` приходят только из реестра сканера (`App.infos`).

Профиль (`jpegHeader`, `imgfile.classify`; спеки 005, 119): ICC важнее EXIF Interop (`R03` = Adobe RGB без профиля у камер). Класс — по содержимому, имя только показывается (у Xiaomi Display P3 зовётся «sRGB EOTF with DCI-P3 Color Gamut»). Порядок: не RGB/без колорантов → `other`, GRAY → `srgb`; колоранты и гамма Adobe → `adobe` (пресет `colorspace.Adobe`, байт в байт как раньше); иначе `colorspace.ParseICC` (матрица и три кривые curv/para, пределы разбора — design 119 §4): ошибка (LUT с A2B0…, битые теги, колоранты не дают белый D50) → `other`, но колоранты sRGB → `srgb` как раньше; колоранты sRGB (допуск 0,003) и `Xform.SRGBCurves()` (кривая sRGB до 2 уровней, 119-14) → `srgb` (v2/v4 sRGB, встроенный в LittleCMS); колоранты P3 D65 (допуск 0,003) → `p3`; остальное → `icc` (ProPhoto, Rec. 709, линейный sRGB, eciRGB). `adobe`, `p3` и `icc` пересчитывает `OpenOriented`: `Xform` из заголовка того же дескриптора вызывается сразу после декода, до любого ресемплинга, — миниатюры, превью, пипетка и экспорт получают одинаковые цвета; бюджет декода для таких фото удваивается (`Color.converts`). `other` — только предупреждение (значок «!» в ленте, вопрос перед экспортом). Для UI `Photo.color` ∈ `srgb|adobe|p3|icc|other`, `Photo.profile` — имя из профиля. PNG и WebP (спека 125): `imgfile.Header` выбирает разбор по подписи (первые 12 байт, не по расширению: WebP под `.jpg` — WebP), класс — тот же `classify`. PNG — `pnghead.go`: чанки идут от IHDR, читается только первый `iCCP` до `PLTE`/`IDAT` (после них, второй и ч/б PNG (тип 0, 4) с профилем `RGB ` — не действуют, как в libpng); `sRGB`, `gAMA`, `cHRM`, `cICP` не читаются, при `iCCP` + `sRGB` решает `iCCP`. Пределы: сначала тип чанка, потом длина — `iCCP` длиннее 1 МиБ (любая длина, и ≥ 2³¹) → `other` без чтения; у прочих чанков длина > 2³¹−1, больше 64 чанков или 16 МиБ пропуска → «без профиля»; профиль сжатым и распакованным ≤ 1 МиБ (`LimitReader`: бомба 1 МиБ → 1 ГиБ не растёт), CRC, метод сжатия 0, ключевое слово 1–79 байт, zlib без словаря FDICT; любая ошибка → `other` «неизвестный профиль». Обход читает только исходный `r` без `bufio` (пропуск — `Seek`). WebP — тот же `webpWalk` (`wantICC`): `ICCP` берётся при флаге ICC (0x20) в `VP8X`, первый, > 1 МиБ → `other`; без флага — не действует (как Chromium). `HeaderShot` у PNG/WebP — тот же `Head` и `Shot{}`; ориентация, время и XMP — нули. Имя профиля — только тег `desc` (ключевое слово `iCCP` не показывается). Пересчёт в `OpenOriented` общий для JPEG, PNG и WebP, альфа не меняется; `.webp` по расширению лента не берёт (профиль WebP нужен WebP под `.jpg`/`.png`).

Файлы выгрузки не в ленте (спека 121): JPEG с COM-меткой «Sosnina Albums» до SOS (`imgfile.Head.Ours`, читается в том же проходе по заголовку) из обхода папки получает состояние `stOurs` — в `photos`, `skipped` и промежуточные списки не входит; финальный отчёт отдаёт пути в `ScanProgress.Ours`, `internal/app/ours.go` пишет счёт в log.txt и шлёт `exports:skipped {n, dir}` один раз на новые файлы. Отдельный файл (`Sources.Files`, 097) остаётся в ленте. Выгрузки до 0.6.0 без метки по имени не узнаются.
