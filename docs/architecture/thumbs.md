## Миниатюры

`library.Cache`: ключ = sha1(путь, размер, mtime), файлы `<ключ[:2]>/<ключ>_t.jpg` и `_p.jpg`; для PNG с прозрачными пикселями (`isOpaque` ложь) — `_t.png`/`_p.png` с альфой, иначе JPEG сделал бы её чёрной. `imgfile.OpenOriented` альфу не трогает (пересчёт цвета — Adobe, P3 и прочие матричные профили — и поворот работают с NRGBA). У `.png` в ключе соль `|png1`: прежние чёрные JPEG-копии не подхватываются. `Cache.File` ищет оба расширения, `/media` ставит `Content-Type` по расширению файла. Один декод оригинала даёт обе копии; все декоды (миниатюры и экспорт) делят бюджет ~500 Мп в памяти (`imgfile.Budget`, файл больше бюджета идёт один); параллелизм ограничен местами генерации (классы мест — абзац ниже: `placesFor` — две трети ядер, не больше 8; хвосты — не больше 24); одновременные запросы одного фото ждут одну генерацию. `Warm` прогревает ленту после сканирования и отменяется при новом сканировании; пока идёт прогрев раскладок открытия (`warmEditor`), он не начинается, а начатый встаёт после текущего фото (`busyGate`, 073-11) — видимые миниатюры `/media` делает по запросу и без него. Ключ Adobe-фото получает суффикс `|srgb1`, фото `p3` и `icc` (119) — `|icc1` (старые блёклые копии не подхватываются; у `srgb`/`other`/без профиля ключ прежний, их кэш цел); фото закрытой папки получает цвет через `imgfile.ReadColor` в `media`. Ответы отдаются с `immutable`-кэшем браузера, поэтому адреса превью в UI несут `?v=5` (`core/media.ts`; v=2 — Adobe, v=3 — PNG с альфой, v=4 — 119: превью P3 и других профилей пересчитаны в sRGB; v=5 — 125: то же для PNG и WebP с профилем, класс PNG меняет соль ключа сам: `p3`/`icc` → `|icc1`, `adobe` → `|srgb1`, PNG без профиля и с `srgb`/`other` — прежний). Плитки `/media/lib` (`max-age=86400`) обновятся сами за сутки.

Превью больших разметок типографии (спека 086, 0.21): JPEG/PNG длинной стороной больше 4096 px подложка строится в Go (`library/markup.go`, ветка в `app/markup.go`) — копия ≤ 4096 px, один раз на файл (путь, размер, время записи), как превью PSD. Миниатюры при переносе папки данных на другой компьютер не переносятся и строятся заново — см. `settings.md` «Папка данных и перенос».

Сведения о снимке (спека 084, 0.21): `App.PhotoAbout(id)` — только чтение, путь берётся из ленты по ID, иначе из проекта (путь от интерфейса не принимается); `paths.CheckLocalPath` идёт до пробы тома. Камера, объектив и параметры съёмки читаются из заголовка JPEG по запросу (не при сканировании), размеры — `imgfile.DimsOf`; результат кэшируется по (путь, размер, время записи), до 512 записей. Вхождения фото («Использовано N раз») берутся из `Editor.PhotoUses` без шага правки (undo) при каждом запросе и в кэш не попадают, поэтому правка альбома меняет строку без повторного чтения файла.

Приоритет мест генерации (спека 090, 0.21; `library/sched.go`, `tails.go`): места делятся на два класса. Запросы окна (`/media`, фоны, плитки шаблонов) берут любое свободное место; прогрев (`Warm`, подписи, превью в фоне) — не больше половины мест и только когда запросов окна нет ни ждущих, ни идущих: начатое он доделывает, нового не берёт. Среди ждущих запросов окна первым получает место новый (после прокрутки важны кадры на экране, а не пролистанные), а запрос, снятый клиентом (плитка ушла из видимой области, ответ не нужен), генерацию не начинает и места не занимает. Превью 2048 запрос окна не кодирует до ответа: уменьшенные из того же декода пиксели ставятся хвостом в ограниченную очередь (`Cache.tails`), и превью дописывает фоновая горутина после ответа; оригинал второй раз не читается. Запрос `_p` на такой ключ ждёт хвост, а при переполненной очереди превью кодирует сам запрос. Отмена на сервере в exe не работает: Wails v2.16–2.17 собирает запрос WebView2 через `http.NewRequest` без контекста (`assetserver_webview.go:109`), `r.Context()` там `Background`, счётчик «снято запросов» в exe всегда 0. Остаётся отмена на стороне фронта (`cancelOnUnmount` снимает `src`, неотправленные запросы не уходят); в браузере стенда (HTTP) работает и серверная.

Оригинал при зуме (128 ступень 2, `app/mediaorig.go`): `GET|HEAD /media/o/<id>` отдаёт файл как есть, без декода и перекодирования, всегда 200 с `Cache-Control: no-store` (условные заголовки и Range снимаются: Wails на WebView2 превращает 304 в 500, а тело копит в памяти целиком — поэтому предел файла 200 МБ и один файл за раз). Путь — из реестра или проекта по ID (`mediaPhoto`), открытие `library.OpenLocal`. Тип по содержимому (JPEG, PNG, WebP), `nosniff`. 415 — цвет не `none/srgb`, кадр больше 100 Мп (по реестру и по заголовку файла, `imgfile.DimsOf`), файл больше 200 МБ или тип не тот; 404 — нет фото или файла (пропавшее — без диска); 405 — другой метод. EXIF и GPS уходят как есть (канал локальный).

Образцы нескачанных наборов (144, `app/packs_tiles.go`): `GET|HEAD /media/lp/<набор>/<вид>/<i>` отдаёт клетку листа образцов, перекодированную Go (JPEG q90), без сети, путей и 304; кэш клеток — LRU 8 МБ в `libpacks`, не `library.Cache`; устройство — `library.md` «Образцы наборов в галереях».

Тихая сверка папок (088, `App.CheckFolders(full)`): `scan` в тихом режиме шлётся только при ≥ 50 новых файлов (иначе чтение незаметно); недоступный том (`osx.Reachable`) не читается и не вешает «Обновить все»; `/media` для фото ленты на недоступном томе сразу отвечает 404 (`reachable` до `Stat`), плитка остаётся серой «нет файла».
